## 一、双平面架构设计 (Dual-Plane Architecture)

为了保证平台运维与各业务团队数据的严格解耦，Spark AI Studio 在架构层面上将系统明确划分为两个平面：

| 架构平面 | 对应路径 | 核心角色 | 职责边界 |
| -------- | -------- | -------- | -------- |
| **控制面 (Control Plane)** | `/platform` | **平台管理员 (Platform Admin)** | 仅负责全局运维：创建多租户组织、任命/注销平台管理员、查看系统级审计日志。**平台管理员绝不会自动加入任何业务组织**。 |
| **数据面 (Data Plane)** | `/organizations`<br/>`/project/:id` | **组织成员 (Owner / Co-owner / Member)** | 承载具体的业务资产：各组织内的项目、工作流 DAG、知识库文档、向量切片、Prompt 模板与私有模型凭证。 |

```
                       ┌─────────────────────────────────────────┐
                       │       平台控制面 (Control Plane)        │
                       │          路由路径: /platform            │
                       │   角色: Platform Admin (具名管理员)     │
                       └──────────────────┬──────────────────────┘
                                          │ 创建组织 (Provision)
                                          ▼
     ┌────────────────────────────────────┴────────────────────────────────────┐
     │                       业务数据面 (Data Plane)                           │
     │                      路由路径: /organizations                           │
     ├────────────────────────────────────┬────────────────────────────────────┤
     │       组织 A (例如 or1)            │       组织 B (例如 finance-ai)     │
     │  Owner / Co-owner / Member         │  Owner / Co-owner / Member         │
     │ ┌───────────────┬────────────────┐ │ ┌───────────────┬────────────────┐ │
     │ │ Project 1     │ Project 2      │ │ │ Project 3     │ Project 4      │ │
     │ │ (工作流/知识) │ (工作流/知识)  │ │ │ (工作流/知识) │ (工作流/知识)  │ │
     │ └───────────────┴────────────────┘ │ └───────────────┴────────────────┘ │
     └────────────────────────────────────┴────────────────────────────────────┘
```

## 二、角色与权限矩阵 (RBAC Matrix)

Spark AI Studio 遵循最小权限原则与敏捷协同哲学，采用三级权限模型：**平台级**、**组织级**与**项目级**。

### 1. 角色级别划分

- **平台管理员 (Platform Admin)**：控制面最高管理员，负责全局组织开通与管理员授权。
- **组织所有者 (Organization Owner)**：组织的法定最高负责人，**全局唯一**。拥有对组织的最高控制权（包括删除组织、转让所有权等）。
- **组织共同所有者 (Organization Co-owner)**：组织的联合管理者，协助 Owner 维护组织设置、邀请成员、调整普通成员角色。
- **组织成员 (Organization Member)**：组织的正式成员，可查看同组织成员列表，并**具备自主创建新项目的权限**。
- **项目所有者 (Project Owner)**：项目的创建者或被委派管理者。拥有项目的设置修改、删除、成员添加及 API 凭证管理权限。
- **项目成员 (Project Member)**：项目内的协同者。

<Callout type="info">
  **协同设计哲学：项目内不设「只读」角色**<br/>
  在 Spark AI Studio 中，凡是加入项目的成员（Member）均拥有平等的读写与运行调试权限。这是因为多智能体工作流是一门重交互、重实验的工程，平等的读写设计极大地促进了跨职能团队的敏捷迭代。
</Callout>

### 2. 详细权限对照表

| 操作能力类别 | 具体操作项 | 平台管理员 | 组织 Owner | 组织 Co-owner | 组织 Member | 项目 Owner | 项目 Member |
| ------------ | ---------- | :--------: | :--------: | :-----------: | :---------: | :--------: | :---------: |
| **控制面运维** | 创建新组织 | ✅ | ❌ | ❌ | ❌ | ❌ | ❌ |
| | 任命/重发平台管理员邀请 | ✅ | ❌ | ❌ | ❌ | ❌ | ❌ |
| | 查看全局系统审计日志 | ✅ | ❌ | ❌ | ❌ | ❌ | ❌ |
| **组织管理** | 修改组织基本信息 (名称/描述) | ❌ | ✅ | ✅ | ❌ | ❌ | ❌ |
| | 删除整个组织 | ❌ | ✅ | ❌ | ❌ | ❌ | ❌ |
| | 转让组织所有权 (Transfer Ownership) | ❌ | ✅ (唯一) | ❌ | ❌ | ❌ | ❌ |
| | 邀请新成员加入组织 | ❌ | ✅ | ✅ | ❌ | ❌ | ❌ |
| | 修改成员角色 (Member ↔ Co-owner) | ❌ | ✅ | ✅ (仅限 Member) | ❌ | ❌ | ❌ |
| | 移除组织成员 | ❌ | ✅ | ✅ (仅限 Member) | ❌ | ❌ | ❌ |
| | 退出组织 (Leave Organization) | ❌ | 需先转让 | ✅ | ✅ | ❌ | ❌ |
| **项目协同** | 在组织下创建新项目 | ❌ | ✅ | ✅ | ✅ | ❌ | ❌ |
| | 继承项目最高管理权限 | ❌ | ✅ (隐式) | ✅ (隐式) | ❌ | ✅ | ❌ |
| | 修改项目设置 (名称/模型配置/Langfuse) | ❌ | ✅ | ✅ | ❌ | ✅ | ❌ |
| | 管理项目 API Keys (新建/注销) | ❌ | ✅ | ✅ | ❌ | ✅ | ❌ |
| | 编排工作流、发布版本、运行调试 | ❌ | ✅ | ✅ | 需进项目 | ✅ | ✅ |
| | 管理知识库文档切片与检索测试 | ❌ | ✅ | ✅ | 需进项目 | ✅ | ✅ |

<Callout type="warn">
  **隐式所有权继承规则（常见疑问解答）**：<br/>
  - **组织管理者自动享有项目最高权**：组织级 Owner 和 Co-owner 会**隐式自动成为该组织下全部项目的 Owner**。即使在某个项目的成员列表中被显式分配为 Member，其底层生效权限依然是 Project Owner（组织级管理权优先于项目角色分配）。因此他们始终拥有创建项目 API Keys、修改模型配置与删除项目等管理权限。
  - **纯项目成员（Pure Member）严格受限**：只有组织角色为 Member、且项目角色也是 Member 的用户，在尝试创建项目 API Key 或修改项目设置时，才会被后端权限严格拦截（返回 403 Forbidden）。
</Callout>

## 三、组织的生命周期与开通流转

组织在系统内经历标准的三态生命周期流转：

```
[平台控制台创建组织] ──► PROVISIONING (待开通)
                                │
                      所有者接受邀请链接注册
                                │
                                ▼
                           ACTIVE (正常生效)
                                │
                         (违规/到期人工冻结)
                                ▼
                          SUSPENDED (已停用)
```

### 1. 平台管理员开通组织

平台管理员在 `/platform` 控制台的「组织」页签中点击 **+ 创建组织**：

![平台控制台组织列表](/images/organizations/01-platform-console.png)

输入组织名称、定位描述以及拟委派的组织所有者邮箱：

![创建组织对话框](/images/organizations/02-create-org-dialog.png)

- 提交后，组织立即创建并进入 `PROVISIONING` 状态；
- 系统生成专属的所有者注册邀请链接（包含高安全熵的随机 Token）。

### 2. 所有者入驻与状态转正

组织所有者打开链接并完成注册激活后，组织状态在数据库内自动由 `PROVISIONING` 转正为 `ACTIVE`：

![组织控制台概览](/images/organizations/03-org-dashboard.png)

此时该组织正式对外开放，所有者即可开展项目协同与团队成员招募。

## 四、组织设置与团队成员管理

### 1. 组织常规设置 (General Settings)

进入组织控制台后，点击组织卡片右上角的 **设置** 图标，打开组织管理页面：

![组织常规设置页面](/images/organizations/04-org-settings-general.png)

- **Organization Name**：修改组织对外展示名称；
- **Description**：修改业务描述；
- **Organization ID**：查看该组织在底层的 UUID 唯一租户标识符（API 调用及系统排查时使用）。

### 2. 成员列表与角色动态调配 (Members Tab)

切换至 **Members** 页签，可查看当前组织已加入的全部成员及待确认的邀请清单：

![组织成员管理列表](/images/organizations/05-org-settings-members.png)

- **成员检索**：支持按姓名或邮箱实时模糊过滤（过滤词直接同步至浏览器 URL 参数 `?q=`，便于分享给同事实时协作）；
- **动态授权**：Owner 或 Co-owner 可直接在下拉菜单中调整成员的角色级别（`Member` ↔ `Co-owner`）；
- **操作保护**：系统禁止任何用户降级自身权限，且禁止 Co-owner 更改同级 Co-owner 或 Owner 的角色。

### 3. 邀请新成员加入组织 (Invite Member)

点击右上角 **Add new member** 按钮唤起邀请对话框：

![邀请新成员弹窗](/images/organizations/06-invite-member-modal.png)

1. 输入受邀员工的企业邮箱；
2. 选择授予的初始角色（`Member` 或 `Co-owner`）；
3. 点击 **Grant access** 提交后，系统生成为期 **7 天** 的专属邀请链接；
4. 邀请发出后展示在「Membership Invites」列表中，支持：
   - **一键复制**：快速复制链接发送至即时通讯工具；
   - **重发邀请 (Resend)**：重发时会自动失效旧 Token 并重置 7 天倒计时；
   - **撤销邀请 (Revoke)**：立即作废该 Token，防止未授权加入。

### 4. 退出组织与所有权转让规则

- **普通成员与 Co-owner**：可随时自主点击页面下方的 **Leave organization** 退出组织；
- **唯一 Owner 退出保护**：作为组织的法定最高负责人，当组织内仅有 1 位 Owner 时，**系统会禁用退出按钮**；
- **所有权转让 (Transfer Ownership)**：Owner 必须在成员列表中指定一名已入驻的成员作为新任 Owner 并确认转让。转让生效后，原 Owner 自动平滑降级为 `Co-owner`，确保组织资产永不流失。

## 五、企业级多租户安全隔离最佳实践

### 1. 数据存储与向量隔离
- **关系型数据隔离**：PostgreSQL 底层在项目、知识库文档与工作流表中统一强制绑定 `organization_id` 与 `project_id` 外键约束，在数据库查询层进行租户过滤，防止越权访问。
- **向量维度隔离**：知识库与向量检索引擎按组织与知识库隔离存储，检索沙箱仅允许在授权范围内的知识库子集间跨库检索。

### 2. 模型凭证与密钥防泄漏
- 各项目可配置独立的模型 API Key（如 OpenAI、Gemini、DeepSeek 等），凭证仅在该项目内可用，跨项目完全不可见；
- 所有敏感凭证在前端界面回显时均经过掩码脱敏处理，防止机密泄露。

### 3. 审计与合规可溯
- 平台控制台提供全量 **Audit Log** 审计追踪，精确记录组织创建、管理员任命、成员角色变更及所有权转让的时间戳、执行人及源 IP。
